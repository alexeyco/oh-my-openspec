# Keeping OpenSpec skills fresh

The plugin bundles OpenSpec's own OpenCode skills — the exact files
`openspec init --tools opencode` writes into a project — so a user installing
this plugin alone gets every upstream workflow (`/openspec-propose`,
`/openspec-apply-change`, `/openspec-archive-change`, …) with no CLI init
step. Those bundles live in `vendor/openspec/` and must track upstream.

## What is vendored

- `vendor/openspec/skills/<id>/SKILL.md` — byte-identical output of the
  pinned CLI, generated with an explicit custom profile that enables every
  known workflow (core + extended).
- `vendor/openspec/manifest.json`:

  ```json
  {
    "package": "@fission-ai/openspec",
    "version": "1.14.2",
    "generatedBy": "1.14.2",
    "skills": ["openspec-apply-change", "…"]
  }
  ```

## How each file stays provable

Freshness is mechanical, not a checklist item: every vendored `SKILL.md`
carries an upstream `metadata.generatedBy` stamp, and the pipeline compares
stamps, manifest, and bytes on every run. The normative gates (sandbox
generation, byte-identical copy, `--check` drift exit codes, mirror
invariant) are specified in
[`openspec/specs/vendor-sync`](../openspec/specs/vendor-sync/spec.md).

## The sync pipeline

1. **Daily CI** — `.github/workflows/vendor-sync.yml` runs on schedule (and
   on `workflow_dispatch`): installs the newest `@fission-ai/openspec`,
   runs `node scripts/sync-vendor.mjs`, mirrors the vendored version into the
   plugin `version` in `package.json`, and opens a PR when the vendor tree
   changed **or** the mirror is off. The PR moves the devDependency pin,
   `vendor/openspec/`, and the plugin version atomically; they always agree
   by construction.
2. **CI on every PR** — `make check` re-runs `--check`, so a merged PR can
   never leave the vendor tree stale against its own `package.json`.
3. **Dependabot** — covers all other npm dependencies and the actions; it
   explicitly **excludes** `@fission-ai/openspec`, because a dependency-only
   bump would break the vendor gate. The vendor-sync PR is the only path
   for that package.
4. **User side** — end users pick up refreshed skills by bumping
   `oh-my-openspec` in `opencode.json`.

## Versioning: a strict mirror

The plugin version **is** the vendored OpenSpec version: a plugin `1.14.2`
bundles exactly the skills generated by CLI `1.14.2`. The number is
machine-owned — only the vendor-sync PR edits `package.json` `version` —
and the mismatch is a build failure, not a review finding; the invariant
and its enforcement live in the
[`vendor-sync`](../openspec/specs/vendor-sync/spec.md) and
[`release-publishing`](../openspec/specs/release-publishing/spec.md) specs.

The trade-off, stated plainly: plugin code merged between two skill releases
gets no npm release of its own; it ships inside the next mirror bump. There
is no way to publish the same version twice, so a fire-and-forget hotfix
just waits for upstream to move. If that ever hurts, revisit — until then,
`version == skills version` is the rule.

## When upstream changes

- New workflow → the sync PR adds its skill; the plugin discovers vendored
  skills from the manifest, so no code change is needed.
- Changed wording/rules → the sync PR's diff is the review surface; CI
  guarantees the stamp, manifest, and bytes stay coherent.
- Hand edits to `vendor/` are impossible to survive the next `--check`;
  the file is also excluded from prettier (`.prettierignore`) to avoid
  formatting drift.
