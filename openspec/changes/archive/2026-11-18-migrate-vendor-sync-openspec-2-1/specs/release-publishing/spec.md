# Release publishing — delta for migrate-vendor-sync-openspec-2-1

## MODIFIED Requirements

### Requirement: The release record is tags and npm, not a CHANGELOG

Releases SHALL use version tags and npm; the plugin `version` in
`package.json` is machine-owned and mirrors the vendored OpenSpec version, so
feature branches add no CHANGELOG. The mirror version SHALL move only in the
daily `vendor-sync` workflow PR or in a migration change that moves the
vendored CLI's layout in a way that breaks vendoring — whether the upstream
release is major or minor. Such a migration regenerates `vendor/openspec/**`
and bumps `version` to the regenerated `manifest.generatedBy` in its own
branch, keeping the `version == manifest.generatedBy` invariant
(`scripts/check.mjs:184-194`) true through the migration. The no-CHANGELOG
half of the rule is unaffected: merged PRs and npm history remain the record
(`CONTRIBUTING.md`, Publishing — version-mirror paragraph;
`docs/vendor-sync.md`, "Versioning: a strict mirror").

#### Scenario: Hotfix window with no upstream release

- **WHEN** a fix must ship before upstream OpenSpec releases again
- **THEN** maintainers dispatch vendor-sync manually; if it produces no PR
  with a new publishable number, the tag is held until the CLI version
  catches up (`CONTRIBUTING.md`, Publishing — "Consequence of strict
  mirroring" paragraph)

#### Scenario: Migration change moves the mirror version

- **WHEN** a migration change moves the vendored CLI's layout in a way that
  breaks vendoring — major or minor alike, as `1.17.0` → `2.0.0` did by
  moving the render location and `2.0.0` → `2.1.0` did by moving the `init`
  scope default and stripping the frontmatter stamp — regenerating
  `vendor/openspec/**` and bumping the `package.json` `version` in the same
  branch
- **THEN** `node scripts/check.mjs` passes the mirror invariant
  (`version == manifest.generatedBy` == the regenerated CLI version), the
  branch adds no CHANGELOG file, and the daily `vendor-sync` workflow keeps
  its exclusive-mover role for every non-migration change

### Requirement: check.mjs enforces six invariant groups

scripts/check.mjs SHALL aggregate failures across six invariant groups
covering package shape, roles, flow skills, vendor metadata, documentation
links, and plugin identity before exiting non-zero. The vendor-metadata
group SHALL validate the manifest and the tree against it: the directory ids
on disk equal `manifest.skills`, every vendored skill's frontmatter `name`
equals its directory id, `manifest.generatedBy` is a plain semver, and the
mirror invariant holds (`scripts/check.mjs:154-194`). It SHALL NOT compare a
per-skill frontmatter stamp against the manifest: CLI 2.1 strips
`generatedBy` from generated frontmatter
(`dist/core/shared/skill-generation.js`, `stripVolatileFrontmatter`), so
`vendor/openspec/manifest.json` is the sole carrier of the vendored version.

#### Scenario: All invariants hold

- **WHEN** every group passes
- **THEN** the script prints `check: ok` and exits 0 (`scripts/check.mjs:233-238`)

#### Scenario: Multiple failures aggregate

- **WHEN** several invariants are broken at once
- **THEN** the script reports all of them in one run (`check: N problem(s):`)
  before exiting 1 (`scripts/check.mjs:233-236`)

#### Scenario: Unstamped vendor tree passes the vendor-metadata group

- **WHEN** `node scripts/check.mjs` runs against a vendor tree generated by
  CLI 2.1 or newer, whose `SKILL.md` frontmatter carries no
  `metadata.generatedBy` key
- **THEN** the vendor-metadata group reports no failure: `name` equals the
  directory id, the manifest is well-formed with a plain-semver
  `generatedBy`, the directories equal `manifest.skills`, and the mirror
  invariant holds — no stamp comparison is attempted

### Requirement: package.json declares homepage, bugs, and author

`package.json` SHALL declare
`"homepage": "https://github.com/alexeyco/oh-my-openspec"`,
`"bugs": "https://github.com/alexeyco/oh-my-openspec/issues"` in the
plain-string npm form,
`"repository.url": "git+https://github.com/alexeyco/oh-my-openspec.git"`,
and
`"author": { "name": "Alexeyco", "url": "https://github.com/alexeyco" }`
with no email key. It SHALL NOT declare a `funding` field, and the
`engines.node` key SHALL be `">=22.20"` — raised from `">=22.18"` by the
OpenSpec 2.1 migration to match the floor the pinned CLI itself declares
(`@fission-ai/openspec@2.1.0` `engines.node: >=22.20.0`).

#### Scenario: Metadata renders on npm

- **WHEN** the next version is published by the tag-driven publish
  workflow
- **THEN** the npm page shows Homepage linking the GitHub repo, Issues
  linking the repo issues URL, and author "Alexeyco" with the profile
  URL; npm accepts the string form of `bugs` (verified 2026-10-17:
  `npm publish --dry-run --json` on a probe package with a string
  `bugs` → `"id": "bugsfmt-probe@0.0.0"`, no warning)

#### Scenario: check.mjs invariants unaffected

- **WHEN** `node scripts/check.mjs` runs against the updated
  `package.json`
- **THEN** it prints `check: ok`: the three keys are additive — group 1
  requires only the presence of `name`/`version`/`description`/`license`
  plus the fixed `type`/`exports`/`files`/`scripts`/devDependency shapes
  (`scripts/check.mjs:39-54`), and group 6's package.json check
  forbids only a stray `pi` section (`scripts/check.mjs:228`)

#### Scenario: engines floor covers the pinned CLI

- **WHEN** `npm install` resolves `@fission-ai/openspec@2.1.0`
- **THEN** the CLI's own `engines.node` (`>=22.20.0`, verified via
  `node -p
"require('./node_modules/@fission-ai/openspec/package.json').engines.node"`)
  is satisfied by the repo's `">=22.20"` floor, and CI's `node-version: 22`
  resolves to a Node that satisfies both

### Requirement: README Node requirement matches engines

The README installation lead-in SHALL state Node.js >=22.20 and remain
consistent with package engines, CONTRIBUTING requirements, and the Node
major used by CI.

#### Scenario: Install section matches engines

  `engines.node` value and to the development requirement
